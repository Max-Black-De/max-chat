# Фронтенд: как пользоваться, как устроено, ограничения

_Документ Фронтенда (F7). Общий [README](../README.md) ведёт Архитектор; здесь — то, что относится к
интерфейсу и коду в `src/ui`, `src/store`, `src/polling`, `src/notifications`. Номера требований — по ТЗ
(Р-n, НФТ-n, Д-n), краевые случаи EC-\* — [docs/edge-cases.md](edge-cases.md). Все значения в примерах
условные._

## Запуск

Node 22 (`.nvmrc`), подробнее — README, разделы «Требования» и «Запуск».

```bash
npm ci
npm run dev        # http://localhost:5173
npm test           # Vitest: unit и компоненты (jsdom), только моки
npm run e2e        # Playwright: Chromium headless, только моки page.route
npm run build && npm run verify:dist
```

> **До финального тестирования не входите в приложение с реальным инстансом** (Р-29). После входа
> приложение сразу запускает опрос очереди (`receiveNotification` → `deleteNotification`) и удаляет
> из неё все чужие уведомления (Р-5, Р-13). Реальный вход — только по сигналу руководителя.

## Вход (ОР-1)

- Поля: «ID инстанса», «Токен» (скрыт, кнопка «показать»), «Адрес API» — в «Дополнительно»,
  по умолчанию `https://api.green-api.com`. Хост не GREEN-API — предупреждение, вход не блокируется
  (EC-T9).
- «Войти» → `getStateInstance`. При `authorized` (и `suspended` — с баннером) открывается основной
  экран, затем один `getSettings`: предупреждения П-1…П-4. Опрос стартует, когда `getSettings`
  завершился (ответ, ошибка или 10 с); при П-1 (задан Webhook URL) — не стартует.
- Учётные данные — только в `sessionStorage` этой вкладки и в памяти; в `localStorage`, логи, URL
  страницы и тексты ошибок токен не попадает (НФТ-3). Перезагрузка вкладки — вход восстанавливается;
  новая вкладка — снова экран входа.
- «Выйти» — опрос и замок вкладки останавливаются, `sessionStorage` очищается; чаты и ленты в
  `localStorage` остаются (п. 1.8).

## Основной экран

- **Слева:** «Сообщения», «+ Новый чат», `idInstance` и «Выйти»; список чатов — по времени последнего
  сообщения, превью в одну строку, время `HH:MM`, счётчик непрочитанных (больше 99 — «99+»).
- **Справа:** баннеры стопкой (сначала ошибки, затем предупреждения, затем «другая вкладка»), шапка
  чата (имя из MAX или номер, номер — подзаголовком), лента и поле ввода.
- **Новый чат:** номер нормализуется (Р-10). Номер уже в кеше — `checkAccount` не вызывается; иначе
  один вызов без автоповтора, на время запроса «Создать», «Отмена» и Esc неактивны (до 15 с).
- **Отправка:** Enter — отправить, Shift+Enter — перенос; пузырь сразу «отправляется», потом
  «отправлено» (без значка) или «не отправлено» с текстом и «Повторить». Счётчик «N/4000» — с 3600
  символов. 429 — до 3 автоповторов; 466 и прочие ошибки — без автоповтора.
- **Приём:** входящие слева, свои с телефона и через API — справа; повтор уведомления второго
  пузыря не даёт (§6.3). Разделители дат «Сегодня», «Вчера», «12 сентября» (Д-6b). Внизу ленты —
  автопрокрутка, иначе кнопка «↓ новые сообщения».
- **Узкий экран** (< 768 px, Д-6e): одна колонка, из чата — «Назад» к списку. **Тёмная тема** — по
  настройке системы (Д-6f), без переключателя.

## Как устроено

```
App
└─ SessionProvider        сессия: вход, getSettings, баннеры, выход (store/session*.ts)
   ├─ LoginScreen         пока не вошли
   └─ ChatsProvider       чаты и кеш номер → chatId (store/chats*.ts, newChat.ts), на сессию
      └─ MessagesProvider ленты, отправка, слияние (store/messages*.ts, sendFlow.ts)
         ├─ MainScreen    вёрстка: список, баннеры, окно чата, диалог «Новый чат»
         └─ Poller        Web Lock вкладки + цикл receive → handle → delete (polling/, notifications/)
```

- **Стор — Context + `useReducer`** (Р-9; подробно — [src/store/README.md](../src/store/README.md)).
  Почему не Zustand: без зависимостей; редьюсеры — чистые функции, тестируются без React (НФТ-9);
  хранение явное через `AppStorage`, потому что нужны версия схемы в ключе
  `maxchat:<idInstance>:v1:…`, режим «только память» при сбое записи (EC-D11) и режим «только чтение»
  во второй вкладке (EC-S4) — готовый `persist` пришлось бы так же оборачивать. Контексты разделены
  (сессия / чаты / ленты), пузырь — `memo`.
- **Эффекты отдельно от состояния:** контроллеры (`sessionController.ts`, провайдеры) вызывают клиент
  `src/api` и диспатчат действия; `fetch`, таймеры, хранилища и логгер инъектируются — тесты без сети.
- **Опрос** (`src/polling/loop.ts`): один receive в полёте, delete после каждого уведомления, backoff
  1 → 30 с после завершения запроса, пауза 1 с после слишком быстрого пустого ответа (§6.1, EC-P17).
  Разбор уведомлений — `src/notifications/route.ts`: вход `unknown`, ручные guards, без исключений.
- **Стили** — обычный CSS в `src/ui/global.css`, CSS-переменные, без UI-китов. Из-за CSP
  `style-src 'self'` — никаких CSS-in-JS и `<style>` во время работы.
- **`data-testid`** — контракт с e2e QA: значения не меняются без согласования.

## Моки и реальный инстанс

| Где              | Что вызывается                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------- |
| `npm test`       | мок `fetch` (`src/test/fixtures/greenApiMock.ts`); реальная сеть в тестах бросает ошибку |
| `npm run e2e`    | моки `page.route` (`e2e/support/greenApi.ts`); любой незамоканный запрос валит тест      |
| реальный инстанс | до финального тестирования — только `getStateInstance`, `getSettings`, `checkAccount`    |

Р-29 (решение пользователя): до финального тестирования на реальном инстансе **не вызываются**
`receiveNotification`, `deleteNotification` и `sendMessage`, не запускаются цикл опроса и пробные
скрипты. `checkAccount` — только по п. 2.11 (номер получателя Р-26, бюджет фронтенда — не больше 3
вызовов). Каждый реальный вызов записывается в журнал QA **до** вызова, без токена, номеров и chatId.
Поэтому реальный вход в само приложение (он запускает опрос) — только на финальном тестировании.
MVP принят на моках.

## Что пишется в консоль

Только `console.warn`, только технические данные (без токена, номеров, chatId и текстов):
сбой `getSettings` (§4.1); один раз — сбой записи `localStorage` (Р-2); уведомление чужого инстанса
и без `instanceData` — только тип (Р-5); битое body — только тип (EC-N7); не-JSON ответ receive —
код и длина (ВА-18); `quotaExceeded` — `method`, `used`, `total`, `status` (§5.5); ошибки receive /
delete с задержкой повтора. Шум из групп, каналов и статусы удаляются молча. e2e
`e2e/console.spec.ts` проверяет, что основной сценарий не даёт в консоли ни ошибок, ни предупреждений.

## Доступность

- Видимый фокус (`:focus-visible`) у всех интерактивных элементов; список чатов — кнопки, Enter
  открывает чат.
- Диалог «Новый чат» модальный: фокус в поле номера, Tab не уходит на фон, Esc / «Отмена» возвращают
  фокус на «Новый чат», после создания — в поле ввода.
- Лента — `role="log"`; баннеры-ошибки — `role="alert"`, остальные — `role="status"`; счётчик
  символов — `aria-live`. Аватары декоративные (`aria-hidden`).
- `dir="auto"` — только у текста пузыря и превью (EC-U5); `lang="ru"`.

## Известные ограничения

- **Опрос в одной вкладке** (Р-12): остальные вкладки того же инстанса только читают; ленты между
  вкладками не синхронизируются. Без Web Locks API (например, `http://<IP>`) — баннер.
- **Очередь у инстанса одна** (EC-P15): если её читает другое приложение или скрипт на том же
  инстансе, часть уведомлений до этой вкладки не дойдёт. Приложение это обнаружить не может —
  остановите посторонних читателей.
- **Токен виден в DevTools → Network и в HAR** (EC-X2): по дизайну API токен — часть пути запроса.
  URL страницы токена не содержит, `Referrer` не отправляется. Не публикуйте HAR и скриншоты Network.
- Только текст и только личные чаты; нетекстовое — заглушка «Сообщение этого типа не поддерживается»
  (Р-11); группы и каналы не показываются. Чат начинается с пустой ленты: истории нет (Р-4, Д-7 не
  делался). Статусов доставки и прочтения нет (Р-14, Д-4 не делался). Удаления чата нет (Р-18).
- После перезагрузки «отправляется» становится «не отправлено» с текстом «Статус неизвестен…»: если
  сообщение всё-таки ушло, его уведомление придёт отдельным пузырём (ВА-20).
- Лимиты тарифа Developer (Р-26) — см. README, раздел «Ограничения».
- Подписи «Сегодня» / «Вчера» пересчитываются при следующей перерисовке ленты, а не ровно в полночь.
- Время в списке чатов — всегда `HH:MM` (Р-21), без даты для старых сообщений.
- Браузеры — последние Chrome, Edge, Firefox, Safari (Р-19); проверялось в Chromium (e2e).

## Тесты фронтенда

- Unit и компоненты: `src/**/*.test.ts(x)`, `src/store/__tests__/`; фикстуры — только условные
  значения из `src/test/fixtures/`.
- e2e: `e2e/chat-send.spec.ts`, `e2e/polling.spec.ts` (Д-2), `e2e/layout.spec.ts` (макет, EC-U3,
  EC-U4, EC-U5, EC-N12, узкий экран), `e2e/console.spec.ts` (чистая консоль); тесты QA — остальные
  файлы `e2e/`.
